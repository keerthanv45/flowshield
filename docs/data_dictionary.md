# Data Dictionary — FlowShield Phase 1

All data described here is **SYNTHETIC**, generated by
`ml/data_generation/generator.py` with a fixed seed. Nothing here
originates from a real payment gateway.

## `PaymentEvent` fields

| Field | Type | Notes |
|---|---|---|
| `event_id` | string | Unique per event |
| `payment_id` | string | Logical payment; one payment can have multiple events (retries) |
| `timestamp` | datetime (UTC) | When the event occurred |
| `amount` | float, `> 0` | Transaction amount |
| `currency` | string | Only `INR` in Phase 1 |
| `payment_method` | enum | `UPI`, `CARD`, `NETBANKING`, `WALLET` |
| `bank` | enum | `HDFC`, `ICICI`, `SBI`, `AXIS`, `KOTAK` |
| `region` | enum | `KA`, `MH`, `DL`, `TN`, `TS`, `AP` |
| `status` | enum | `created`, `processing`, `success`, `failed` |
| `failure_reason` | enum or null | Required iff `status == failed`; must be null otherwise |
| `latency_ms` | float, `>= 0` | End-to-end processing latency |
| `customer_id` | string | Drawn from a pool of 6,000 synthetic customers |
| `attempt_number` | int, `>= 1` | 1 = first attempt, 2+ = retry |

Failure reasons: `timeout`, `network_error`, `insufficient_funds`,
`authentication_failed`, `bank_declined`, `technical_error`, `unknown`.

## Modeled correlations (not independent rows)

- **Payment method → baseline success rate.** UPI and WALLET are modeled as
  more reliable than NETBANKING (see `METHOD_BASE_SUCCESS_RATE`).
- **Bank → baseline multiplier.** SBI and KOTAK are modeled as slightly
  flakier than HDFC, independent of any incident (`BANK_SUCCESS_MULTIPLIER`).
- **Failure reason → latency.** `timeout`, `network_error`, and
  `technical_error` push latency up (`LATENCY_BOOST_FAILURE_REASONS`).
  `insufficient_funds` deliberately does **not** — a declined-for-funds
  response is fast, not hung.
- **Amount distribution.** Right-skewed (lognormal), clipped to
  `[10, 200000]` INR — most transactions are small, a long tail is large.
- **Retries vs first attempts.** `attempt_number > 1` gets a small success
  probability boost (transient issues resolving) and added latency
  (retry/backoff overhead) relative to `attempt_number == 1`.
- **Failure-reason mix depends on payment method.** e.g. `CARD` skews
  toward `authentication_failed` / `insufficient_funds`; `NETBANKING`
  skews toward `bank_declined` / `timeout`.

## Recovery potential (business-rule reference, not yet modeled as a field)

Documented here for Phase 2+ (the future recovery agent), not implemented
in Phase 1:

| Failure reason | Recovery potential | Rationale |
|---|---|---|
| `timeout` | High | Often transient — retry/alternate route can succeed |
| `network_error` | High | Often transient |
| `technical_error` | Medium | Sometimes transient, sometimes systemic |
| `authentication_failed` | Medium | Retry with a different auth flow may help |
| `bank_declined` | Low | Often a genuine decline from the issuing bank |
| `insufficient_funds` | Low | Retrying the same payment rarely helps |
| `unknown` | Low | Insufficient information to act confidently |

## ML-ready splitting

See `ml/evaluation/split.py`. Splits are **time-based** (train = earliest
70% of the period, validation = next 15%, test = final 15%), not randomly
shuffled, to avoid leaking information across incident windows.
